======================================================================
2. PROJECT OVERVIEW
======================================================================

Project name: StoneRate

StoneRate is a marketplace and operational platform for construction materials. It currently supports:

1. Buyers
2. Stone Sellers
3. Sand Sellers
4. Admin
5. Transport-related workflows

The application allows Sellers to upload material samples, Buyers to compare samples and raise rate requests, Admin to prepare quotations and control platform information, and Sellers to manage orders and operational queues.

The project uses one shared application, shared database, and shared authentication system, but Stone Seller and Sand Seller operational modules are separated where their business rules differ.

Images:
Cloudflare R2

Image workflow:

1. Frontend submits an image through multipart/form-data.
2. Backend validates the image using Multer and Sharp.
3. Backend uploads the image to Cloudflare R2.
4. The permanent R2 URL is saved in PostgreSQL.
5. The same saved URL is reused in Seller, Buyer, Admin, quotation, and order views.

Stone and Sand images use the same R2 infrastructure but separate object prefixes.

Examples:

- Stone samples: existing Stone sample folder/path
- Sand samples: sand-seller-samples/<sellerPublicId>/...
- Seller profiles: existing profile-image folder/path

Do not create another R2 bucket or another R2 utility unless strictly necessary.

11. SAND SELLER BUCKET INFORMATION
======================================================================

Bucket conversion is configured per Seller and per Admin-approved Sand material.

Database table:

seller_sand_bucket_information

Important: the correct table name is exactly:

seller_sand_bucket_information

Do not use the incorrect name:

sand_seller_bucket_information

The Profile page contains one compact Bucket Information card.

Profile behavior:

1. Seller clicks Manage.
2. Seller searches the Admin-approved Sand material catalogue.
3. Seller adds only the materials the Seller handles.
4. Seller enters cubic feet per bucket.
5. Each material is saved separately.

Example:

Morang
1 bucket = 30 cubic feet

River Sand
1 bucket = 28 cubic feet

Sample upload behavior:

- Upload dropdown shows all Admin-approved materials.
- Configured materials are active/selectable.
- Unconfigured materials are faded/locked.
- Clicking an unconfigured material shows guidance:
  Profile > Bucket information > Material
- Backend also blocks upload if bucket information is absent.

Conversion:

material rate per feet = rate per bucket / cubic feet per bucket

Example:

₹600 per bucket / 30 cubic feet = ₹20 per feet

Important snapshot rule:

When the sample/order is created, the applicable conversion is stored as a snapshot so later profile changes do not silently alter historical rates.

19. SAND YARD SHARED ADMIN/SELLER WORKFLOW
======================================================================

A shared Sand Yard request is created after the Buyer accepts a Sand quotation.

Shared table:

sand_yard_order_requests

Expected flow when Sand Seller responds first:

Buyer accepts Sand quotation
-> shared Sand Yard request is created
-> request appears in the selected Sand Seller's Requests tab
-> Seller accepts/rejects
-> Seller queue token and estimated time are saved
-> Admin Active Order Details reads the same Sand Yard record
-> Admin sees Filled by SAND_YARD and current status/details

Expected flow when Admin responds first:

Admin opens Active Order Details
-> Admin fills Sand Yard Details
-> backend automatically accepts the pending Sand Seller request
-> permanent material token is generated
-> Upcoming loading entry is created
-> shared request is marked ACCEPTED
-> filled_by is ADMIN
-> request disappears from Seller Requests
-> entry appears directly in Seller Upcoming
-> Seller does not accept again

Important foreign-key fix:

sand_order_loadings.order_id references the legacy sand_orders table, not the main orders table.

For shared main-order Sand Yard loadings, use:

order_id = NULL

The main order relationship remains in:

sand_yard_order_requests.order_id -> orders.id

Latest requested/developed integration files:

- backend/src/routes/admin.routes.js
- frontend/src/api/adminApi.js
- frontend AdminActiveOrderDetails component

Admin API function:

saveAdminSandYardDetails(deliveryId, details)

Admin endpoint:

PUT /api/admin/active-orders/:deliveryId/sand-yard

This endpoint should:

1. Lock the matching sand_yard_order_requests row.
2. If pending, generate the next permanent material queue token.
3. Insert an Upcoming sand_order_loadings row with order_id = NULL.
4. Mark request accepted.
5. Set filled_by to admin.
6. Return the saved Sand Yard details.
7. If already accepted, update the existing loading/request rather than create a duplicate.

22. IMPORTANT PREVIOUS ERRORS AND FIXES
======================================================================

1. PostgreSQL 42P08 inconsistent parameter types

Fix by explicitly casting reused SQL parameters, such as:

$13::varchar
$8::numeric

2. Duplicate seed primary keys

Use:

ON CONFLICT DO NOTHING

when either the primary key or normalized unique field can conflict.

This was needed for:

- buyer_feet_options
- sand_material_catalogue Morang seed

3. Blank React pages

Common causes found:

- Using variables before declaration
- Child components referencing parent-scope variables such as displaySeller
- Missing icon imports such as Layers or RefreshCw
- Invalid ESLint-disable rules

Always run a real JSX bundle check, not only node --check.

4. R2 invalid metadata header

Encode material metadata with encodeURIComponent.

5. sand_order_loadings foreign-key error

Main orders IDs cannot be inserted into sand_order_loadings.order_id because that column references sand_orders.
Use order_id = NULL and link through sand_yard_order_requests.

6. Wrong bucket-information table name

Correct:

seller_sand_bucket_information

Incorrect:

sand_seller_bucket_information

Cross-material movement:
- A vehicle can be selected for any material within the same parent TR

  operational responses.
- Duplicate actual vehicle numbers across child deliveries are de-duplicated.
- When duplicates exist, retain the most operationally advanced record;
  if statuses are equal, retain the most recently updated record.

  selected.
- Display remaining demand only for the selected material.

Formula:
remaining quantity for selected material
= selected material requested quantity
- loaded quantity already recorded for that material

Example:
- 20mm requested: 2 ton
- 40mm requested: 2 ton
- Selected material: 20mm
- Previously loaded for 20mm: 0 ton
- Remaining to load shown in the form: 2 ton

If 0.5 ton is already loaded for 20mm:
- Remaining to load: 1.5 ton
- Supporting text: 0.5 ton already loaded of 2 ton

The second information box in the form should describe the quantity previously
recorded for the selected vehicle, which is separate from the selected
material's total remaining demand.
